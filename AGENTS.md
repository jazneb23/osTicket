# AGENTS.md

## Cursor Cloud specific instructions

This repo is a **strangler-fig migration demo**: a TypeScript orchestrator
(`orchestrator/`) drives Cursor SDK agents that extract logic from the legacy
osTicket PHP app and prove behavioral **parity** with golden fixtures before
opening a PR. The osTicket web app is the host being strangled, exercised mainly
through a PHP harness. See `.cursor/skills/onboarding/runbook.md` for the full
command/env reference — this section only records non-obvious startup caveats.

### Environment source of truth

- The cloud environment is defined by `.cursor/environment.json`, which points at
  `.cursor/Dockerfile` (Docker-in-Docker + Node 22 + `gh`). That Dockerfile is
  the source of truth — make durable environment changes there, not in a saved
  snapshot. `install` runs `.cursor/install.sh` (`npm ci`); `start` runs
  `.cursor/start.sh` (starts `dockerd`, then `scripts/ci-docker-bootstrap.sh`).
- If you land on a VM where `docker` is missing or hits a permission error
  (can happen on just-in-time VMs not built from the Dockerfile): start the
  daemon with `sudo service docker start`. Docker 29 needs
  `/etc/docker/daemon.json` with `storage-driver: fuse-overlayfs` **and**
  `features.containerd-snapshotter: false` for the DinD storage driver to work.
  If your shell isn't yet in the `docker` group, run docker commands via
  `sg docker -c "<cmd>"`.

### Running the parity gate (the real check)

- The gate is `npx tsx orchestrator/ci-parity-check.ts`. Docker Compose must be
  up first (`bash scripts/ci-docker-bootstrap.sh` — idempotent). The harness runs
  legacy PHP inside the `web` container via `docker compose exec`, so parity
  needs Docker, not a local PHP.
- Parity needs a seam manifest at `orchestrator/manifests/<TICKET>-manifest.json`
  or the runtime `orchestrator/.state/<TICKET>-manifest.json`. Manifests are
  **runtime-generated by the cartographer stage (needs `CURSOR_API_KEY`) and are
  not committed**, so with a clean checkout the CI parity check *skips* (it does
  not fail). For MOD-25 the harness script is auto-pinned in
  `orchestrator/lib/manifest.ts`, so a minimal `.state/MOD-25-manifest.json` with
  `{"ticketId":"MOD-25"}` is enough to run the verifier against the committed
  golden fixtures (a non-mutating parity check). `orchestrator/.state/` is
  gitignored.
- The verifier writes a `parity.json` report into the ticket fixture dir at
  runtime; it is untracked — do not commit it.
- Never edit fixtures or invent `expected` values to make a run pass (see
  `.cursor/rules/*`). Parity is sacred.

### No build/lint step; `tsc` is not a gate

- The orchestrator runs via `tsx` (no compile step) and there is no meaningful
  `npm test`/build script. `npx tsc --noEmit` fails **by design** (`tsconfig.json`
  sets `types: []` and does not include `@types/node`, so Node globals like
  `process`/`fs` are untyped). Do not treat `tsc` as a required check — the
  parity gate is the gate.

### osTicket web app (`:8080`) is optional and schema-only

- `scripts/ci-docker-bootstrap.sh` imports the schema and seeds only what the
  parity harness needs. There is **no admin/agent account, no help topics, and no
  company config**, so the client portal renders "Support Ticket System Offline"
  and the "Open a New Ticket" form is not functional. The staff Agent Login page
  (`/scp/login.php`) does render. Do not expect a working ticket-submission UI
  without substantial extra configuration; the product action for this repo is
  the parity gate, not the osTicket UI.
- `include/ost-config.php` is generated by the bootstrap and is gitignored — do
  not commit it.

### Secrets

- The full pipeline/listener need external secrets (`CURSOR_API_KEY`,
  `LINEAR_API_KEY`, `GITHUB_REPO_URL`, `GITHUB_DEMO_BRANCH`, optional
  `SLACK_WEBHOOK_URL`). None are required to run Docker Compose or the MOD-25
  parity verifier described above.
